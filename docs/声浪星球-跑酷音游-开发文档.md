# 1. 项目概述与核心玩法

## 1.1 一句话定位

> **声浪星球** = 把一首歌变成一颗可以"跑着打"的星球。**跑酷的操作感 + 音游的判定与音乐驱动。**

## 1.2 世界观与主题

- **1 个枢纽 + 3 颗曲境星球**：`home`（枢纽）→ `desert`《晴天》→ `cave`《夜曲》→ `base`《稻香》→ 回到枢纽。
- **"场景 = 歌曲 = 星球"**：每颗星球的关卡结构、机关与节奏均由该曲的**节拍与段落**驱动。
- **主角**：龙形宇航员（`createDragonAstronaut`），在星球表面跑酷、收集"音浪晶体"、激活传送装置。
- **核心叙事钩子**：**"你玩出来的歌"** —— 玩家沿星球前进的过程，本身就是对该曲的一次演奏。

## 1.3 核心循环（三级）

```
┌─────────────────────────────────────────────────────────────┐
│ 微循环（秒级）  踩点 → 判定(Perfect/Good) → 连击↑ → 得分↑   │
│                          ↓ 失误(Miss) → 连击归零             │
├─────────────────────────────────────────────────────────────┤
│ 中循环（分钟级）进入星球 → 跑跳收集 → 集齐晶体 → 激活传送门   │
│                          ↓ 关卡结算 → 评级 S/A/B/C           │
├─────────────────────────────────────────────────────────────┤
│ 宏循环（会话级）选歌/上传 → 生成星球 → 逐星通关 → 图鉴/解锁   │
└─────────────────────────────────────────────────────────────┘
```

## 1.4 核心玩法：跑酷 × 音游

当前原型只实现了**跑酷半身**，回归目标是补上**音游半身**，二者融合：

| 维度 | 跑酷半身（现有，M0–M2） | 音游半身（回归目标，M3） |
|---|---|---|
| 操作 | 移动（WASD/摇杆）+ 跳跃（空格）+ 冲刺（Shift） | **2 键**：跳跃 / 滑行；动作需**踩点** |
| 关卡对象 | 音浪晶体、传送装置、山顶 | **音符（Note）**：绑拍点的收集/动作目标 |
| 核心机制 | 收集、穿越、任务进度 | **判定**（Perfect/Good/Miss）、**连击**、**计分** |
| 音乐作用 | 背景节拍（`BeatClock`，仅驱动"踩点跳"加成） | **音乐驱动关卡生成**（BPM/onset/RMS/分段） |
| 结算 | 任务卡（1/3、0/1） | **评级面板**（分数 / 最大连击 / S·A·B·C） |

**融合模型（判定对象）**：把现有的每一类关卡动作都升级为"**可判定的节奏事件**"——

1. **踩点收集**：触到晶体时，按与目标拍点的偏差判定；
2. **踩点跳跃**：起跳对齐拍点 → 判定（**已实现雏形**：`jump.perfect = BeatClock.inWindow()`，给 `V0_PERFECT` 加成）；
3. **漏拍**：拍点划过而目标未达成 → Miss。

## 1.5 与"最初音游"的对齐与差异

| 最初音游（总开发文档 v1.0） | 现状 | 回归后（M3 完成态） |
|---|---|---|
| 上传任意歌 → 分析 → 自动生成 3D 关卡 | ❌ 无 | ✅ M3-B 实现 |
| 2 键（跳跃/滑行）打节奏 | ❌ 移动+跳 | ✅ M3-C 实现 |
| Perfect / Good / Miss 判定 | ❌ 无（仅跳跃加成） | ✅ M3-A 实现 |
| combo 连击 / score 计分 | ❌ 无 | ✅ M3-A 实现 |
| S / A / B / C 结算评级 | ❌ 无 | ✅ M3-A 实现 |
| 能量条 / 5 段镜头 | ❌ 无 | ⚠️ 可选（见 6.5） |
| 音频分析管线（BPM/onset/RMS/分段） | ❌ 无 | ✅ M3-B 实现 |
| "你玩出来的歌"反哺 | ❌ 无 | ✅ M3-B 实现（摘要卡） |

> **差异红线**：**保留现有 4 场景美术与视觉复刻成果**。回归是"叠加音游层"，不是"推倒重建跑酷"。这一点直接决定 M3-A/C 的工程约束（见 3.5）。

## 1.6 玩法红线与设计约束（**强制执行**）

| 编号 | 约束 | 说明 |
|---|---|---|
| **R1** | **视觉零漂移红线** | 定帧机位下的四场景 `heroC` 必须与 M1 基线**逐位一致**（home `.551/.712` · desert `.512/.762` · cave `.373/.635` · base `.397/.766`）。音游层**只允许**做"逻辑 + HUD + 逐帧动画"，**不得新增/移动场景几何**，除非走 M3-B 的"重新定标"流程。 |
| **R2** | **随机流纪律** | 生成期任何新增随机外观元素**必须**走 `dseq(seed)` 独立流（源码 `dseq` @200），**绝不消耗全局 `rnd()`**。改现有元素只允许"改参数区间/颜色/几何参数"，不得改 `ri()/rr()` 的**调用次数**。 |
| **R3** | **操作零写入** | 静止于出生点且无输入时，对 `hero` 零写入（`PlayerController.update` 已有早退分支），保证静止取景逐位可复现。 |
| **R4** | **单文件、无构建** | 全部逻辑在 `声浪星球.html` 一个 IIFE 内；唯一外部依赖是本地 `three.min.js`。**不引入打包器/框架**。 |
| **R5** | **音频需用户手势解锁** | 浏览器自动播放策略：`AudioContext` 必须在用户手势（点击/按键）后 `resume()`（现有 `initAudio()` 已处理）。 |
| **R6** | **免费不侵犯版权** | 内置曲目使用可授权素材；"上传任意歌"仅在**本地分析**，不上传服务器、不内置受版权曲目音频。 |

# 2. 目标平台与技术选型

## 2.1 目标平台

| 项 | 目标 |
|---|---|
| **首选平台** | 桌面浏览器：Chrome / Edge ≥ 110、Safari ≥ 16（macOS） |
| **兼容平台** | 移动触屏：iOS Safari、Android Chrome（竖屏/横屏，触屏虚拟摇杆+按键） |
| **分辨率** | 自适应（`resize` 已接线）；基准视口 1672×941（参考图 1:1 尺度） |
| **帧率目标** | 桌面 60fps；移动 ≥ 30fps |
| **运行方式** | 本地打开或静态托管（`python -m http.server`）；**无网络依赖**（three.min.js 本地） |
| **不支持的场景** | 需要 GPU 的极端低端机、IE/旧内核（无障碍降级策略见 7.6） |

## 2.2 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 渲染 | **Three.js r128**（本地 `three.min.js`） | 低多边形、程序化几何、无贴图依赖为主；少量 canvas 程序化贴图（`ptex`） |
| 语言 | **原生 JavaScript（ES5 风格 IIFE）** | 单文件、无转译；`'use strict'` |
| 音频 | **Web Audio API** | `AudioContext`（实时：`kick/hat/scheduleAudio`）；**新增** `OfflineAudioContext`（离线分析）、`decodeAudioData`（上传解码） |
| UI/HUD | **DOM + CSS** | 玻璃拟态卡片（`.glass`）；`--px = 100vh/941` 做等比缩放 |
| 数学/工具 | 自研确定性随机（`srand/rnd/rr/ri/pick` + `dseq`） | 保证生成可复现 |
| 构建 | **无** | 直接编辑单文件；门禁脚本用 Playwright + Python |

## 2.3 单文件架构的取舍

**为什么单文件**：黑客松交付要"双击即开、零环境"；便于 1:1 视觉复刻的逐帧比对。

**代价与补偿**：
- 代价：无模块系统、无类型检查、单文件 3000+ 行。
- 补偿：**严格的模块化命名**（每个模块一个 `var Xxx = {...}`）、**权威锚点表**（附录 A）做行号定位、**四道门禁**做回归。

## 2.4 音频子系统选型（M3 关键）

| 能力 | API | 用途 | 平台约束 |
|---|---|---|---|
| 实时节拍 | `AudioContext` + 定时调度 | 现有 `kick/hat`、`BeatClock` 锁拍 | 需手势解锁（R5） |
| **离线分析** | `OfflineAudioContext` | 解码后提取 PCM → BPM/onset/RMS/分段 | Chrome/Safari 均支持 |
| **文件解码** | `decodeAudioData` | 上传 mp3/wav → 转 PCM | 建议限制时长（如 ≤ 6 分钟）与格式 |
| 音频驱动关卡 | 自研 `ChartGen` | onset 序列 → 音符落点 | 见 5.3 |

## 2.5 性能与兼容性约束

- **Draw calls 红线**（`tools/budget.js` 校验）：`home < 700` / `desert < 700` / `cave < 1900` / `base < 1000`。
- **三角面**：现基线 home 34,245 / desert 31,160 / cave 28,062 / base 43,777。
- **音游 HUD 为 DOM**，不占 draw call；**节拍脉冲**复用现有晶体材质自发光（不新增 draw call）。
- **内存**：上传音频分析须在分析后释放 `AudioBuffer`，避免长时间占用。

## 3.3 主循环时序（每帧顺序）

现有顺序（`loop` @2584，`FREEZE` 下整段跳过 → 保定帧零漂移）：

```
Input.poll()
→ BeatClock.update(dt)
→ Lane.update(dt, cur)                         // M3-OP：跑道换道插值（easeOutCubic）
→ PlayerController.update(dt, cur, SCN[cur])   // M3-OP：自动前进 + 车道接管（x 由 Lane 决定）
→ Collectible.update(dt, cur, SCN[cur])
→ Portal.update(dt, cur, SCN[cur])
→ CameraRig.update(dt, cur)
→ VFX.update(dt, cur)
→ updateScene(cur, dt)          // 既有环境动画
→ render
→ HUD.sync()
```

**M3 扩展后**：

```
Input.poll()
→ BeatClock.update(dt)
→ [M3-A] Score.tick(dt)                  // 连击衰减/断连计时（可选）
→ [M3-C] Slide.update(dt, cur, SCN[cur])
→ PlayerController.update(...)
→ Collectible.update(...)   // 触到晶体 → Judge.onCollect()
→ Portal.update(...)        // 激活 → Judge.finish() → ResultPanel.show()
→ CameraRig.update(...)
→ VFX.update(...)
→ [M3-A] RhythmHUD.sync()               // 仅在数据变化时重渲染
→ updateScene(cur, dt)
→ render
→ HUD.sync()
```

> **约束**：所有 M3 逐帧逻辑**必须**包在 `if (!FREEZE){...}` 内，否则破坏门禁 1（零漂移）。

## 3.5 零漂移架构约束（**最重要**）

> 视觉复刻是北极星（R1）。回归音游**不得**让定帧取景发生哪怕一个像素的变化。工程手段：

1. **逻辑/HUD 优先**：判定、计分、连击、评级、音游 HUD **全部是纯逻辑 + DOM**，不触碰场景几何 → 天然零漂移。**M3-A 与 M3-C 必须严守此边界**。
2. **逐帧动画是安全的**：晶体旋转/浮动（`Collectible.update` 已有）、节拍脉冲（改材质 `emissiveIntensity`）不会改变 `hero` 与几何，`__info().heroC` 不受影响。
3. **新增场景物体（M3-B）走 `dseq`**：自动生成的音符视觉标记必须走独立随机流；且**会改变关卡布局** → 触发"重新定标"流程（见 7.5）。
4. **`FREEZE` 守卫**：截图门禁下 `loop` 跳过全部 M3 更新；任何新模块都要在 `FREEZE` 分支外不可达。

```js
Song = {

  difficulty: 1|2|3                  // 展示难度
}
```

### 5.1.2 音频分析 `Analysis`（M3-B）

```js
Analysis = {
  duration,                 // 秒
  bpm,                      // 估计 BPM
  offset,                   // 首拍偏移（秒）
  onsets: [t0,t1,...],      // onset 时刻（秒）
  energies: [e0,e1,...],    // 逐小节/逐拍能量（0..1）
  rms: Float32Array,        // RMS 包络
  sections: [ {t, kind:'intro'|'verse'|'chorus'|'outro'} ]
}
```

### 5.1.3 谱面 `Chart` / 音符 `Note`（M3-A/B）

```js
Chart = {
  songId, bpm, offset,
  notes: [ Note, ... ]      // 按 beat 升序
}
Note = {
  id, beat,                 // 目标拍点（拍为单位）
  type: 'collect'|'jump'|'slide',
  x, z,                     // 世界坐标（沿可玩带布置）
  hit: false, judged: null  // 运行时
}
```

### 5.1.4 局内状态 `GameState`（扩展）

```js
// 现状：level, counters, portal, reset/add/get/taskDone
// M3 扩展：
GameState = {
  level, counters, portal,
  score: 0, combo: 0, maxCombo: 0,
  judge: { perfect:0, good:0, miss:0 },
  acc: 1.0
}
```

### 5.1.5 结算 `Result`

```js
Result = {
  level, songId,
  score, maxCombo, acc,                 // acc = (300P+150G)/(300*(P+G+M))

}
```

## 5.3 关卡/谱面生成（M3-B 核心管线）

```
上传/内置音频
   │ decodeAudioData
   ▼
PCM (AudioBuffer)
   │ OfflineAudioContext 离线渲染 + 逐帧分析
   ▼
┌──────────────────────────────────────────┐
│ ① BPM：自相关 / onset 间隔直方图 估计       │
│ ② onset：谱通量（spectral flux）峰值检测    │
│ ③ RMS：能量包络 → 强弱段                    │
│ ④ 分段：基于 RMS + 频谱变化 → intro/verse/  │
│        chorus/outro                        │
└──────────────────────────────────────────┘
   │
   ▼
ChartGen：onset → Note
   · beat_i = t_i / (60/BPM)
   · z 轴：按时间线性推进（可玩带 Z_MIN→Z_MAX）
   · x 轴：由 onset 强度/频段映射到 band 内
   · 段落：chorus 加密（每拍），intro/outro 稀疏（每 2–4 拍）
   · 弱起/强拍：映射为 collect / jump / slide
   │
   ▼
注入 LEVELS.levels[level].chart  →  Collectible 按 chart 布置晶体
```

**约束**：自动生成的视觉标记走 `dseq(seed=songId)`；且**改变关卡布局 → 触发重新定标**（7.5）。

## 5.4 判定与计分数值表（**M3-A 核心数值**）

| 判定 | 窗口（|Δ| 占单拍比例） | ≈毫秒 @118bpm | 得分 | 连击 |
|---|---|---|---|---|---|
| **Perfect** | ≤ 0.09 拍 | ±46ms | 300 | +1 |
| **Good** | ≤ 0.22 拍 | ±112ms | 150 | +1 |
| **Miss** | > 0.22 拍 / 漏拍 | — | 0 | 归零 |

- 现有 `CFG.W_BEAT = 0.09` 即 Perfect 窗口，直接复用。
- **准确率**：`acc = (300·P + 150·G) / (300·(P+G+M))`。
- **评级**：

| 评级 | 条件 |
|---|---|
| **S** | acc ≥ 0.95 **且** miss = 0 |
| **A** | acc ≥ 0.88 |
| **B** | acc ≥ 0.75 |
| **C** | acc < 0.75 |

> **注（causeway 实现口径）**：本表以「拍」表述判定窗口（依据 118 BPM）。第 5 关《超频长阶》BPM = 158，按拍换算过窄，故单赛道关改用**绝对毫秒** `Perfect ≤ 80 ms / Good ≤ 160 ms`（见《声浪星球-关卡设计-超频长阶》§7.4）；`acc` 公式与评级阈值（S 需 `miss = 0`）完全沿用本表。

## 7.5 回归测试流程（含"重新定标"）

```
改代码 → 跑四门禁 → 门禁 1 逐位一致 → 视觉回归无新差异 → 文档锚点重校 → 提交
```

**重新定标（M3-B，改布局）**：
```
1. 改代码（音符走 dseq）
2. 跑 quad.js → 记录新 heroC 基线（预期会变）
3. 人工确认新基线符合设计意图（非回归性偏移）
4. 更新四份文档的 heroC 基线与锚点表
5. 跑 palette.py 确认无系统性色差劣化
6. 提交（commit message 注明"重新定标"）
```

> **教训（复用）**：批量锚点重校 = `difflib.SequenceMatcher` 生成 old→new 行映射 + 脚本按行定位替换 + **强制人工复核**；**不得纯脚本**（历史上"复合区间被单值规则二次命中"踩过坑）。

# 附录 B：术语表

| 术语 | 含义 |
|---|---|
| **跑酷半身 / 音游半身** | 本文对"现有跑酷玩法"与"待回归音游玩法"的形象划分 |
